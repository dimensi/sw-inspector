# ADR 0004: Explicit development actions alongside passive inspection

- Status: **Accepted for selected/fixed-list namespaces and selected Cache Storage entry deletion, confirmed worker update/unregister, explicit bounded manifest loading and confirmed JSON messaging/opt-in listeners — 2026-10-21**
- Date: 2026-10-19
- Supersedes: the blanket cache-delete and worker-update/unregister prohibitions in ADR 0001 only for explicit confirmed selected namespace/fixed-list batch deletion, explicit direct retained-request entry deletion, or confirmed update/unregister of one retained registration. Explicit bounded manifest loading is also accepted; explicit confirmed JSON messaging and opt-in document listeners are accepted. Other bounded-diagnostics rules remain in force. The execution and permission boundary in ADR 0002 is unchanged; S4 adds authenticated panel-hide cleanup within that route.

## Context

The user requested plans for Cache Storage deletion, Service Worker management, Web App Manifest inspection, and sending/receiving SW messages. The first enabled action is deletion of one selected cache namespace. Changing that promise without precise targets, document identity and transport outcome semantics would make existing stale-result suppression insufficient: suppressing a result cannot undo a write.

## Accepted scope

Keep passive inspection as the default. Enable explicit prepare/confirm/commit for one selected Cache Storage namespace. Prepare checks current presence and retains the name; commit invokes `caches.delete(name)` once. True means applied, false means absent, rejection means failed. Cache Storage offers no atomic generation comparison; the site may recreate the name. Known outcomes refresh overview; applied/absent invalidate only that name’s inventory/details/measurement. Unknown outcomes retain a warning and an explicit Refresh action. Bind each action to the inspected document and a retained target; never automatically retry an uncertain mutation. A timeout after possible submission is outcome unknown. Cache deletion remains subject to browser API concurrency; they are not transactions.

C2 also enables a complete `caches.keys()` snapshot of at most 100 names. Zero names cannot prepare a ticket; more than 100 rejects without truncation and instructs individual deletion. Confirmation lists the origin, exact count and every name. Commit deletes only the retained list, sequentially, checking current identity before each call; one rejection does not stop other current targets. Known per-name outcomes survive inside the handler, while navigation still suppresses publication through the existing runner/transport boundary and yields unknown. No automatic retry or claim that the origin stays empty is made. Applied/absent names alone invalidate their snapshots and UI data; overview refresh is independent from the receipt.

C3 enables one selected entry. On explicit user request (2026-10-21), **Delete entry** executes directly without a confirmation dialog; namespace and batch deletion retain confirmation. The entry-only controller path freshly prepares and commits the exact local ticket within the same generation, never by confirming shared controller state after an await. Reset/selection/navigation before dispatch suppresses the old operation. No Undo or automatic retry is provided. Inventory behavior: inventory snapshots retain the Cache handle and original Request with their existing five-minute TTL and twelve-snapshot eviction bound. Prepare requires an exact snapshot/index key with a canonical nonnegative integer index, matching cache and unexpired snapshot; no URL reconstruction or new cache open is allowed. Commit revalidates the retained snapshot and current document immediately before ordinary `Cache.delete(retainedRequest)` without ignore options. True means applied, false absent, rejection failed. Applied/absent invalidate every snapshot and selected details/measurement for that cache; reread only that cache and leave the response selection empty. Missing cache returns to Cache Storage. Preview does not extend snapshot lifetime. Unknown outcomes use the existing warning and never retry.

W5 enables confirmed update/unregister for one retained registration from an overview of at most 100 registrations. Overview IDs retain exact registration and active/waiting references for five minutes and are replaced on Refresh; over-limit snapshots remain diagnostic-only. Prepare and commit validate document identity, expiry, registration membership and captured installing/waiting/active references. Update resolves as applied with no activation guarantee; unregister true is applied, false absent, rejection failed. Existing controlled pages and Cache Storage remain independent. After any known or unknown outcome, reread the overview once only for the same document; preserve the action result if that read fails and disable stale handles until Refresh. No automatic retry, worker start/stop/restart/skipWaiting, or atomicity claim is added. Native acceptance remains separate in TESTING.

M5 enables explicit **Load manifest** for the first discovered manifest link. Discovery and source expansion are passive. The request uses CORS, link-derived credentials/referrer policy and redirect-follow; it reads at most 262144 decoded response bytes with an 8000 ms deadline covering headers and body. Snapshot TTL is 60 seconds with at most eight retained DOM links; page identity, first-element identity and link attributes are rechecked before dispatch and after awaited work. No arbitrary URL input, automatic request/retry, icon/image fetch, installation or installability claim is enabled. Bounded source remains local and excluded from metadata exports; displayed declarations/reconstructed URLs are not Safari’s processed manifest.

S4 enables explicit confirmed JSON submission to one retained active/waiting worker. Prepare/commit validate exact registration/worker identity, slot, document, five-minute registration TTL and current leased message session. Payloads are parsed JSON (including primitives/null), capped at 16 KiB UTF-8 and 16384 code units; send the raw value once without an application envelope. Posting is submission, not delivery, and can change website state. Optional cooperative replies use our own transferred port with a five-second timeout and request ID correlation; ordinary container messages are never correlated. Start listening is opt-in and adds only our listeners for the inspected document. Buffer and panel rows are limited to 500/2 MiB, with bounded previews and explicit dropped counts. A ten-second lease, renewed by serial one-second reads even during confirmation, bounds cleanup after panel loss. Hide, Refresh, navigation, permission failure and disposal stop polling and best-effort close owned listeners/ports; returning never resumes listening automatically. Send settlement reads only the session buffer, never an overview that would invalidate its handles. No payload/draft persistence, export, console logging, telemetry, generic commands or foreign-port interception is enabled. These exceptions do not permit arbitrary network probes, offline emulation, broad host permissions, arbitrary code evaluation, telemetry, or background capture.

Retain the devtools-page relay, activeTab permission boundary, synchronous JSON jobs, existing visual system, and metadata-only default exports. Do not introduce direct-panel eval or a content-script fallback without new reproducible evidence.

## Activation and consequences

The implementation contract and limits live in the [development design](../plans/2026-10-19-development-design.md); small tasks and dependencies are indexed in the [roadmap](../plans/README.md). C1, C2, C3, W5, M5 and S4 activate this scoped decision together with PRODUCT, AGENTS, UI/manifest/package descriptions and release copy. Do not describe planned capabilities as shipped.

Feature-specific acceptance requires a disposable fixture and native Safari evidence. Reconcile accepted decisions back into ADR 0001 with an explicit superseded-part link. The project retains the distinction between an application message submission and delivery, update completion and activation, registration and control, cache presence and offline behavior.
